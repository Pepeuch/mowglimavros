# MM-HERE4-CAN2-20260928 — HERE4 node 124 passive CAN2 diagnosis

Disposition: BLOCKED — HERE4 application does not provide GNSS/compass telemetry; MM-801/HW-MAV-005 remains open.

Repository `/workspaces/mowglimavros`, branch `main`, HEAD `781946d7ba8a595d7a472781763ffac6800545da`. Hardware baseline: Pixhawk 5X / ArduRover 4.7.1, HERE4 on Pixhawk CAN2. Read alongside `MM-WHEEL-TRIAL-20260928` and `MM-PIXHAWK-PASSIVE-AUDIT-20260928`; older HERE4-on-CAN1 notes refer to previous topology.

## Read-only method and result

- FCU cached live values: `CAN_P2_DRIVER=2`, `CAN_P2_BITRATE=1000000`, `CAN_D2_PROTOCOL=1`, `CAN_D2_UC_NODE=10`, `GPS1_TYPE=9`, `GPS1_CAN_OVRIDE=124`, `GPS1_RATE_MS=125`. `CAN_SLCAN_CPORT=1` targets CAN1, so existing SLCAN configuration does not expose CAN2. No Rock SocketCAN interface or installed DroneCAN CLI was available.
- A guarded 30.000 s CAN2 receive capture used temporary `MAV_CMD_CAN_FORWARD param1=2` only. Its 12 activation/refresh ACKs succeeded; `param1=0` stop ACK succeeded. A separate 6 s receive check saw FCU heartbeats and zero CAN_FRAME/CANFD_FRAME, confirming forwarding off. FCU remained disarmed/MANUAL. Capture/decoder are local ignored files under `.agent/checkpoints/`; raw logs are not promoted.
- 1,582 MAVLink CAN_FRAME records, zero CANFD_FRAME; every forwarded frame carried zero-based bus 1 (CAN2). Source node 124 produced exactly 30 broadcast `uavcan.protocol.NodeStatus` transfers and 6 complete, nine-frame `uavcan.protocol.GetNodeInfo` responses to Pixhawk node 10. No other source-124 broadcast was present: no GNSS Fix/Fix2/Status, magnetic field, or diagnostic log in this interval.
- NodeStatus: 30/30 `health=0 HEALTH_OK`, `mode=2 MODE_MAINTENANCE`, `sub_mode=0`, `vendor_specific_status_code=13`; uptime 4,924→4,953 s, transfer IDs consecutive modulo 32, gaps 0.997–1.003 s. No reboot/drop observed in this 30 s window. This confirms CAN2 communication and compatible bit rate, but does not reveal the stored `CAN_BAUDRATE` setting.
- GetNodeInfo (same in six responses): name `com.cubepilot.here4`; hardware major/minor `4.19` = board ID `0x0413` = 1043; software major/minor `2.0`, optional version flags zero, commit and image CRC unavailable. CubePilot [HERE4 hwdef](https://raw.githubusercontent.com/CubePilot/GNSSPeriph-release/release/Here4/hwdef.dat) defines board ID 1043 and that node name. The reported 2.0 matches the ArduPilot **DroneCAN bootloader** version, not a proven AP_Periph application version.
- FCU `/mavros/gpsstatus/gps1/raw` remained `fix_type=0`, `satellites_visible=0`, lat/lon zero, eph/epv 65535. FCU emitted `PreArm: DroneCAN: Node 124 unhealthy!` and `PreArm: Compass 2 not found`; these are FCU messages, not `mowgli-gps`/Universal GNSS USB diagnostics.

## Interpretation and evidence boundary

The [DroneCAN NodeStatus definition](https://raw.githubusercontent.com/dronecan/DSDL/master/uavcan/protocol/341.NodeStatus.uavcan) defines mode 2 as maintenance, including bootloader use. ArduPilot [bootloader CAN source](https://raw.githubusercontent.com/ArduPilot/ardupilot/master/Tools/AP_Bootloader/can.cpp) reports software version 2.0, sets maintenance mode, and places `check_good_firmware()` in the vendor status code when firmware checking is enabled. Its [firmware check enum](https://raw.githubusercontent.com/ArduPilot/ardupilot/master/libraries/AP_CheckFirmware/AP_CheckFirmware.h) defines 13 as `FAIL_REASON_BAD_CRC`. These four observed fields and the absence of application sensor output together strongly indicate that node 124 is running its bootloader and that its AP_Periph application image fails CRC. The exact CubePilot bootloader build and reason for the CRC failure were not independently read, so retain this as a high-confidence diagnosis rather than a verified flash-memory fault. [CubePilot's HERE4 manual](https://github.com/CubePilot/cubepilot-docs/blob/master/here-4/here-4-manual.md) also documents maintenance mode following a failed firmware update; no update history is established here.

This evidence supports **A, CAN communication works but application GNSS/compass output is absent**, with stronger evidence for an application boot failure than for an internal GPS receiver defect. It contradicts **B, recurrent node reboot** during the capture and **C, a CAN bit-rate mismatch preventing communication**. **D, GPS receiver baud/nonresponse** is untestable while the application is not running; no internal serial traffic was visible.

The following requested HERE4-side parameters were **not read**: `CAN_BAUDRATE`, `CAN_NODE`, `CAN_FDMODE`, `GPS_AUTO_CONFIG`, `GPS1_TYPE`, `GPS1_RATE_MS`, internal SERIAL/GPS port and baud, `COMPASS_ENABLE`, and application firmware version. Passive broadcast/NodeInfo does not carry them. The standard ArduPilot CAN bootloader [accepts NodeInfo/update/restart services but not param.GetSet](https://raw.githubusercontent.com/ArduPilot/ardupilot/master/Tools/AP_Bootloader/can.cpp), so a read-only GetSet would likely fail while it remains in this state. Do not infer node settings from FCU settings or board build defaults. The physically functioning bus is consistent with the FCU's 1 Mbit/s setting.

## Next step / unblock condition

Have the operator/vendor inspect the HERE4's firmware update history and bootloader/application status using CubePilot's official process. Any firmware reflash, reset, or power cycle requires a separate explicit authorization and procedure. Before MM-801 GNSS acceptance, require operational NodeStatus mode, application version, GNSS and compass broadcasts, healthy FCU GPS1 and compass, then read internal parameters if still relevant. Do not bypass FCU prearm checks. This audit made no FCU/node parameter change, injected CAN frame, arming, motor command, restart, or firmware update; the temporary receive forwarding was explicitly stopped.
