An independent 7 s check after each run saw seven FCU heartbeats and zero `CAN_FRAME`/`CANFD_FRAME`, confirming forwarding off. FCU remained connected, armed, MANUAL. The 5% Status decoder initially interpreted the 18-bit RPM field as a big-endian integer and printed implausible ±130k RPM. Offline correction using DroneCAN's little-endian scalar byte order gives node 1 up to 630 RPM; the local script is corrected. [DroneCAN Status DSDL](https://dronecan.github.io/Specification/7._List_of_standard_data_types/) and [generated canard decoder](https://raw.githubusercontent.com/am32-firmware/AM32/main/Src/DroneCAN/dsdl_generated/include/uavcan.equipment.esc.Status.h) support the field layout. The zero RawCommand finding means only that no such frame was present in the MAVLink-forwarded receive stream; it does **not** prove ArduPilot transmitted no RawCommand on CAN1. Neither trial measured `SERVO_OUTPUT_RAW` or RC input during the pulse, so acceptance by Rover and the output stage remain unlocalized. A subsequent read-only MAVROS cache check found `RC_OPTIONS=65` (bits 0/6: ignore RC receiver and skip neutral-stick arming check, **not** ignore MAVLink overrides), `RC_OVERRIDE_TIME=3.0 s`, `RCMAP_THROTTLE=3`, `RC3_DZ=30`, `RC3_TRIM=1515`, and servo functions 73/35/74 on outputs 1/2/3. These values do not by themselves explain the lack of output. [Rover 4.6 RC_OPTIONS reference](https://ardupilot.org/rover/docs/parameters-Rover-beta-V4.6.0.html#rc-options-rc-options). Do not raise throttle again without diagnosing this gap.

A separate **passive** 20 s MAVROS ESC telemetry capture followed while the operator manually rotated **only the right wheel** and confirmed the left wheel stayed still. ROS slots had 60 samples each: slot 0 had 26 nonzero RPM samples, range 0–1,038 RPM, 0 A; slots 1 and 2 stayed 0 RPM/0 A. It directly contradicts the older right-wheel → ESC2/index 1 observation. The physical mapping changed or earlier evidence was misattributed; no cause is established. Preserve both dated observations and use current evidence for further diagnosis. Command slot mapping remains unknown.

## First authorized 5% attempt — aborted before propulsion

The operator gave `GO ARMÉ` for one bounded 5%/10 s `MANUAL_CONTROL` trial while the FCU was `connected=true`, `armed=true`, `MANUAL`; `RC_OVERRIDE_TIME=3.0 s`, MAVROS source 255 and target 1, bridge disabled, and RC outputs were neutral. The guarded local script `.agent/checkpoints/manual_control_5pct_probe.py` passed offline codec checks before deployment. Its initial run activated CAN1 forwarding (`COMMAND_ACK result=0`) and sent 60 **neutral** `MANUAL_CONTROL` messages; outgoing MAVLink was observed as sysid 255/compid 191, target 1, `x=y=z=r=0`. It **aborted before the positive pulse** because its CAN decoder incorrectly required a full 16-byte MAVLink 2 `CAN_FRAME` payload. MAVLink 2 truncates trailing zero bytes, so valid short frames were discarded. It then sent 2 s of neutral and explicitly disabled forwarding (`COMMAND_ACK result=0`). No positive throttle message was published, no motor movement was caused by this attempt, and no physical motor result may be inferred.

The decoder was corrected to accept payload length >=9 and zero-pad the MAVLink CAN_FRAME layout to 16 bytes. A separate 5 s **passive** CAN1 capture, with forwarding on/off acknowledged and no manual/motor command, then yielded 741 CRC-valid `uavcan.equipment.esc.Status` packets: node 1=247, node 2=249, node 3=245; no RawCommand frames were seen in that passive interval. An independent 7 s postcheck saw eight FCU heartbeats and zero `CAN_FRAME`/`CANFD_FRAME`, with FCU still connected, armed, MANUAL. The old operator GO was consumed by the aborted run. **Do not repeat the positive pulse without a fresh GO.** The current local script is prepared but has an explicit `--execute-go-armed` gate; default execution is offline-only.
